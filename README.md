# nhm-assist

nhm-assist is a collection of python workflows presented in Jupyter notebooks for evaluating, running and interpreting [National Hydrologic Model (NHM)](https://www.sciencebase.gov/catalog/item/626c0d67d34e76103cd2ce4a) subdomain models using [`pywatershed`](https://github.com/EC-USGS/pywatershed), a python package for simulating hydrologic processes motivated by the need to modernize important, legacy hydrologic models at the USGS, particularly the Precipitation-Runoff Modeling System (PRMS, Markstrom et al., 2015). nhm-assist allows users to:

- evaluate hydrofabric element connections such as hydrologic response unit connections to streamflow segments, segment routing order, and gage placement accuracy;
- display NHM subdomain parameter values on interactive maps and plots;
- run the NHM subdomain using `pywatershed` and create output for chosen variables;
- display NHM subdomain output values, such as recharge or actual evapotranspiration, on interactive maps and plots; and
- display simulated and observed streamflow for model gages on interactive plots.

Select interactive maps and plots generated by nhm-assist are saved locally in .html format and displayed in a web browser.

## Part 1: Using nhm-assist

### Install

**1. Install [pixi](https://pixi.sh)**, the dependency and environment manager nhm-assist uses, per the [official instructions](https://pixi.sh/latest/#installation).

**2. Clone the repository.** Navigate to your projects folder and run:

```bash
git clone https://code.usgs.gov/wma/hytest/nhm-assist.git
cd nhm-assist
```

Cloning puts you on `main`, which includes active development work. For the latest tagged release, run `git checkout 1.1.1` (or any other tag).

**3. Install the environment.** From the repository root:

```bash
pixi install
```

This reads `pyproject.toml` and `pixi.lock` and installs a reproducible Python environment under `.pixi/envs/default/`. Every later `pixi run …` command uses it automatically.

> **Looking for the legacy `mamba env create -f environment.yaml` flow?** Use the [`1.1.1` release](https://code.usgs.gov/wma/hytest/nhm-assist/-/releases/1.1.1) (`git checkout 1.1.1`). The `main` branch is pixi-only.

### Get an NHM subdomain model

If you have been provided an NHM subdomain model, download it from the USGS [HyTEST](https://hytest-org.github.io/hytest/doc/About.html) OSN storage pod:

```bash
pixi run python pull_domain.py --name=willamette_river
```

This creates `domain_data/` and adds the example subdomain for the Willamette River watershed. That folder is where the workspace flow looks for bundled examples, so anything downloaded there can be copied into a project. Set `NHM_ASSIST_EXAMPLES_DIR` to keep them elsewhere.

### Quick start

```bash
pixi run setup
```

This drops you into a guided menu. Work through the top four options in order:

1. Set the workspace root — defaults to `nhm-workspace` alongside the cloned repo, outside it
2. Create a project
3. Copy an example model, which becomes the active model
4. Show the notebook folder and how to open it, generating the notebooks first if needed

Then run `0_workspace_setup.ipynb` first, from the project's notebook directory.

### How a workspace is laid out

Your projects, models, generated notebooks, and outputs all live **outside the cloned repository**. The repository stays the source of code, notebook templates, and the shared `data_dependencies`.

```text
<workspace>/
  <project>/
    notebooks/nhm/
    project_config/active_model.yaml
    models/
      <model>/
        config/
        inputs/source_data/
        outputs/runtime/
```

A workspace holds one or more projects; a project holds one or more models and one set of generated notebooks; each project records one active model. Notebooks resolve that active model from `project_config/active_model.yaml` and write gage files, model outputs, and exported HTML maps and plots into `models/<model>/outputs/runtime/`. Nothing is written back into the repository. This works the same on macOS, Windows, and Linux.

Each project also gets two things that make your work reviewable in git:

- a `jupytext.toml` pairing every notebook to a `.py` file beside it, so diffs show code rather than notebook JSON
- a `.vscode/` folder recommending the [Jupytext Sync](https://open-vsx.org/extension/caenrigen/jupytext-sync) extension and configuring it to sync when you open and when you save — this works in both VS Code and Kiro, since Kiro is Code OSS-based and installs Open VSX extensions

The guided menu covers the common path. The equivalent commands, run from the repository root, are:

| Goal | Command |
| --- | --- |
| Create a workspace | `pixi run workspace-init <workspace-root>` |
| Create a project | `pixi run project-create <workspace-root> <project-name>` |
| Copy an example model | `pixi run model-copy-example <workspace-root> <project-name> <model-name> Walla_Walla` |
| Set the active model | `pixi run project-set-active-model <workspace-root> <project-name> <model-name>` |
| Generate one workflow's notebooks | `pixi run notebooks-create-project <workspace-root> <project-name> nhm` |
| Generate every workflow's notebooks | `pixi run notebooks-create-project <workspace-root> <project-name> all` |

Generating is safe to re-run on notebooks that already exist: cell content is always preserved, and only pairing metadata is brought back in line. Each run prints the folder it wrote to and tells you which of `created`, `already configured`, or `metadata updated` applied to each notebook.

### Opening the notebooks

Open the project folder in whichever tool you use:

```bash
jupyter lab <workspace-root>/<project-name>/notebooks/nhm
code <workspace-root>/<project-name>
```

In VS Code or Kiro, open the **project** folder rather than the notebook subfolder — see [When syncing silently stops working](#when-syncing-silently-stops-working) for why that matters.

Then point the notebook at this project's pixi environment, `.pixi/envs/default`.

> **Choosing the kernel is yours to do.** nhm-assist registers no Jupyter kernel and writes none into notebook metadata, so your editor asks the first time and remembers per notebook. In VS Code or Kiro either route works — "Python Environments…" pointed at `.pixi/envs/default`, or "Jupyter Kernel…" if you have already made one. The two label the same interpreter differently, which is exactly why the choice is left to you.

### Plots and maps

nhm-assist interactive plots are created using [plotly](https://plotly.com/python-api-reference/). These figures facilitate evaluation of NHM subdomain model parameters and output. Interactive plots open in new browser tabs and are exported to `notebook_output_files/html_plots` under the active model's runtime folder.

Interactive maps are created using [folium v0.18.0](https://python-visualization.github.io/folium/v0.18.0/index.html) and visualize geospatial elements of the NHM subdomain; select maps embed plotly figures. Maps open in new browser tabs and are exported to `notebook_output_files/html_maps` under the same runtime folder. You can interact with these maps and embed them in webpages, presentations, or anywhere else outside the notebooks.

**Note:** in some map outputs, the field labeled `nhru` corresponds to the NHM hydrologic response unit identifier, `nhm_id`.

#### Plot interaction

![plotly guide](./data_dependencies/images/plotly.png)

1. Hovering your mouse in the top-right corner of the plot will display a **modebar**. The buttons in this bar allow the user to export the plot as a static figure png, zoom, pan, zoom in, zoom out, autoscale axes, or reset axes.
1. Legends are also interactive. Left-clicking a legend item will display or hide its associated data on the plots.
1. With the zoom tool selected from the modebar, click and drag the mouse to draw a box and zoom to a specific region in the plot to see higher detail, e.g, clicking and dragging in the daily data plot a user can see
1. Hover over data in the plots to view a pop-up containing detailed information for that point

#### Map interaction

![folium guide](./data_dependencies/images/folium.png)

1. Maps contain a thumbnail regional map in the upper left-hand corner that can be collapsed by left-clicking on the upper left corner of the thumbnail map. Below the thumbnail map are tools to zoom in/zoom out or expand the map to full screen.
1. Left-click map on hydrofabric elements (HRU's, gages, segments) to display a pop-up with more detail regarding the element. The displayed information will vary with the type of hydrofabric element that the user clicks and the active notebook.
1. Click the layer control button in the lower right-hand corner to bring up the layer control. Here, users can select a basemap, activate/hide specific map layer, and turn labels on or off. **Note** As a user toggles layers on/off, they are redrawn in order of activation, e.g., the first layer a user activates will be rendered on the bottom. Layer order may affect pop-up display. When viewed in a browser tab, refresh the tab to reset layer order.
1. Left-click the measure tool and trace lines or polygons to estimate distances or areas.
1. Left-click and drag the map to pan. Use the scroll wheel to zoom in or out.

## Part 2: Developing nhm-assist

Contributors use the **same** workspace flow as everyone else. There is no separate in-repo notebook directory and no contributor-only launcher — you work against your own project exactly as a user would, so the path you exercise is the path they get.

Only the `.py` templates are committed; `*.ipynb` is gitignored.

### Dev mode

Set up a project once, as in Part 1, then generate its notebooks in **dev mode**:

```bash
pixi run dev-mode <workspace-root> my-test-project nhm
```

That command generates the notebooks in the same place a user sees them, and pairs each one back to its real source template in `src/workflow_templates/`, so **saving the notebook writes your edit straight into the repo** where git can see it. It prints the folder and how to open it; it does not start Jupyter.

`dev-mode` defaults to the `nhm` workflow. Pass another as the third argument:

```bash
pixi run dev-mode <workspace-root> my-test-project nhf
pixi run dev-mode <workspace-root> my-test-project pest
```

Dev mode and ordinary generation differ in exactly one respect:

| | `notebooks-create-project` (and `setup`) | `dev-mode` |
| --- | --- | --- |
| Paired `.py` | Beside the notebook, via the project's `jupytext.toml` | The real template in `src/workflow_templates/` |
| Edits land in | Your project | The nhm-assist repo |

Everything else — how the notebook finds the active model, where outputs go — is identical, which is the point.

> **The numbered notebooks are one shared set.** `0`–`6` and `add_pois_to_parameters` live once, in `src/workflow_templates/common/`, and both the `nhm` and `nhf` workflows render them. NHF's own parameter-building notebooks stay in `src/workflow_templates/nhf/`, and PEST renders only `src/workflow_templates/pest/`.
>
> So a dev-mode edit to notebook 2 in an `nhm` project changes the template NHF renders too. Check both if your change is not fabric-neutral. The templates read fabric-specific behaviour from the active model's config rather than from per-workflow copies.

**Where your workspace can live.** Dev mode pairs through a *relative* path, so your workspace and this repo must share a parent directory below the filesystem root — both somewhere under your home directory, for example. A workspace on a separate volume or Windows drive cannot be dev-paired, and `dev-mode` says so rather than silently writing the template to the wrong place. Ordinary generation is unaffected and works from anywhere.

### Which direction the sync flows

**The notebook drives the sync. The template is passive.** Opening the notebook pulls the template's latest content in; saving the notebook pushes your edits back out. Saving the **template** updates nothing — jupytext reports that it "is not a paired notebook".

Opening syncs automatically in JupyterLab. In VS Code or Kiro it only does so with the Jupytext Sync extension installed and sync-on-open enabled, which generated projects come configured for.

Three consequences worth internalizing:

- **After a `git pull`, reopen the notebook before working in it.** Otherwise your first save pushes the stale notebook over the template you just pulled.
- **Never edit the notebook and the template between syncs.** jupytext keeps whichever file is newer and discards the other, silently and with exit code 0.
- **An agent editing a template counts as one of those two editors.** If a coding agent edits `src/workflow_templates/…` while you have that notebook open, your next save wins and its work is gone. Close the notebook before an agent edits its template, and reopen it afterward. See [AGENTS.md](./AGENTS.md) for the full rule.

If your project's `.vscode/settings.json` is missing, or has `onNotebookDocumentOpen` set to `false`, run `pixi run setup` and choose **Repair editor settings for this project** once. Then re-run notebook generation for that project as well: repaired settings alone do not fix a notebook whose own jupytext metadata predates this feature, and its next save would re-stamp a stale header onto the shared template.

### Leaving dev mode

Run ordinary generation over a project that is currently in dev mode:

```bash
pixi run notebooks-create-project <workspace-root> my-test-project nhm
```

This is cell-safe: it rewrites only pairing metadata, switching the notebook back to the project's own `jupytext.toml`. `pixi run setup`'s "Generate NHM notebooks" does the same thing, since the menu always generates in local mode.

It does drop the notebook's pairing to `src/workflow_templates/`, so **sync and commit any dev-mode edits before switching back** — otherwise they stay stuck in your workspace notebook and never reach the shared template.

### When syncing silently stops working

The `.vscode/settings.json` written into each project points Jupytext Sync at the pixi interpreter that actually has `jupytext` installed. When that file is not read, the extension fails **silently** — no error, no popup, saves simply stop syncing. Two resolution rules explain nearly every case:

- **Editors read `.vscode/settings.json` only from a root folder you opened, and never walk up from a subfolder.** Open `<project>/notebooks/nhm` directly and the project's settings are ignored. Open `<project>` instead and browse down.
- **Every `jupytextSync.*` setting is window-scoped, so in a multi-root workspace a folder's `.vscode/settings.json` is skipped entirely.** If you work in a `.code-workspace` listing more than one folder, copy the setting into that file's own `"settings"` block:

  ```jsonc
  "settings": {
    "jupytextSync.pythonExecutable": "<repo>/.pixi/envs/default/python.exe"
  }
  ```

  Use `python` instead of `python.exe` on macOS and Linux. Forward slashes work everywhere and avoid JSON escaping.

A stale user-level `jupytextSync.pythonExecutable` also overrides the project's. If it points somewhere without `jupytext`, the extension gives up rather than falling back to auto-discovery, so clear it or fix it. To see what it actually chose, run **Jupytext Sync: Show Logs** from the command palette.

### Environments other than `default`

`default` is the only environment you need for running or developing the notebooks: it carries the analysis stack, the test and lint tooling, and conda-forge's `proj-data` grids. Those grids, plus `PROJ_NETWORK=OFF` on activation, are why `pyproj` works behind an SSL-inspecting firewall without per-machine setup.

Two others exist and are rarely needed directly:

- **`ci`** — `default` minus `proj-data` and the lint tooling (`ruff`, `pre-commit`), so continuous integration skips that download. 1.9 GB against `default`'s 2.7 GB.
- **`dev-future`** — a separate solve group tracking the next major versions of `pywatershed` and `dataretrieval`. Expect real test failures there; it exists to see what is coming.

### Troubleshooting

#### A package version does not match `pixi.lock`

Python adds a per-user package directory (`~/.local/lib/pythonX.Y/site-packages`, or `%APPDATA%\Python\PythonXY\site-packages`) to `sys.path` *ahead* of this environment's own. It is keyed by Python version rather than by project, so a `pip install --user` run from any other project can override versions locked here — and neither `pixi install` nor `pixi list` can see it, because both read the lock file rather than `sys.path`. The first cell of `0_workspace_setup.ipynb` checks for this and names the affected packages. Launching Jupyter through pixi avoids it entirely.

#### Upgrading from an older checkout

nhm-assist used to register two Jupyter kernels, `Python (nhm-assist)` and `Python (nhm-assist dev)`, and stamp one into every notebook it generated. It no longer registers or stamps anything.

Existing notebooks lose the stale kernel metadata the next time you generate them, but the two registered kernels stay in your Jupyter configuration, where they keep appearing in your editor's kernel list. Removing them is a one-time cleanup you run yourself in a terminal.

**Check whether you have them.** From the repository root:

```bash
pixi run jupyter kernelspec list
```

If `nhm-assist` or `nhm-assist-dev` appear in that list, remove them:

```bash
pixi run jupyter kernelspec remove nhm-assist nhm-assist-dev
```

It asks you to confirm; answer `y`. Run it once per machine — these kernels are registered for your user account, not per project. Use `pixi run` so the command finds the `jupyter` that ships with this environment; a bare `jupyter` may not be on your `PATH`.
