# GridMET Climate Drivers — Hovenweep HPC

This folder contains everything needed to run gridMET climate driver generation on the Hovenweep HPC cluster.

## Important: Compute Nodes Cannot Access External Data

Hovenweep compute nodes are behind a Fortiguard web filter that blocks outbound HTTP/HTTPS to external servers. This means **SLURM jobs on compute nodes cannot access OPeNDAP/THREDDS data** (the source for gridMET).

**Recommended approach:** Run `run_all_models.py` on a **Data Transfer Node (DTN)** which has direct Internet2 access:
- `hw-dtn1.gs.doi.net`
- `hw-dtn2.gs.doi.net`

DTNs are purpose-built for pulling external data and have fast, unrestricted internet access.

## Workflow Overview (Recommended)

```
Local machine                         Hovenweep HPC
─────────────                         ─────────────
1. Run Submit notebook cells 1-4
   → generates transfer_to_hpc.ps1

2. Run transfer_to_hpc.ps1  ────────→  Files land in HPC_WORK_DIR
                                        │
3. SSH to DTN (-K for Kerberos)         │
   ssh -K user@hw-dtn1.gs.doi.net       ▼
                                    4. conda activate nhm-gridmet
                                        │
                                        ▼
                                    5. nohup python run_all_models.py > run_all_models.log 2>&1 &
                                        → processes 10 models sequentially
                                        → ~10 min per model (~100 min total)
                                        → gdptools handles parallelism internally
                                        │
                                        ▼
                                    6. Output: domain_data/<model>/*.nc

7. Run retrieve_from_hpc.ps1 ←──────  Pull .nc results back locally
```

### Why not SLURM?

The gridMET workflow requires live OPeNDAP access to `thredds.northwestknowledge.net:8080`. Compute nodes block this. SLURM scripts are retained in case HPC admins whitelist the endpoint in the future.

### Why DTN over login node?

- DTNs have direct Internet2 access (faster downloads)
- DTNs are designed for data-intensive workloads
- Avoids login node etiquette concerns for long-running processes

| File | Purpose |
|------|---------|
| `run_all_models.py` | **Main entry point.** Processes all 10 child models sequentially. Handles SSL, error recovery, progress tracking, and summary. |

## Prerequisites

1. **VPN** — Must be connected to access Hovenweep
2. **Kerberos auth** — `ssh -K <user>@hw-dtn1.gs.doi.net` must work
3. **miniforge3** — Installed at `/home/<user>/miniforge3` on Hovenweep
4. **Conda env** — Run `bash setup_hpc_env.sh` once to create `nhm-gridmet`
5. **Geopackages** — Run the fabric setup locally first so `domain_data/<model>/GIS/model_layers.gpkg` exists for each child model

## Running on the DTN

```bash
# SSH to a data transfer node
ssh -K <user>@hw-dtn1.gs.doi.net

# Navigate to work directory
cd <HPC_WORK_DIR>

# Activate environment
source ~/miniforge3/etc/profile.d/conda.sh
conda activate nhm-gridmet

# Run in background (persists if SSH disconnects)
nohup python run_all_models.py > run_all_models.log 2>&1 &

# Monitor progress
tail -f run_all_models.log
```

### Re-running after failures

The script skips models that already have output files. If the THREDDS server throttles you (I/O failure errors), wait a few minutes and re-run — it will pick up where it left off.

## SSL Certificates on HPC

Conda environments ship their own `certifi` which doesn't include DOI/USGS intermediate certificates.

**Fix (already built into scripts):**
```bash
export SSL_CERT_FILE=/etc/pki/tls/certs/ca-bundle.crt
export REQUESTS_CA_BUNDLE=/etc/pki/tls/certs/ca-bundle.crt
```

Plus a Python-level fix in `run_all_models.py` and `run_gridmet_single.py` that patches `ssl._create_default_https_context` to use the system CA bundle. This keeps full SSL verification enabled.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `Web Page Blocked` / `NetCDF: Authorization failure` | Compute nodes block external HTTP | Use DTN nodes instead of SLURM |
| `NetCDF: I/O failure` | THREDDS server throttled you | Wait a few minutes, re-run (cached files are skipped) |
| `SSL: CERTIFICATE_VERIFY_FAILED` | Conda's certifi missing DOI certs | Scripts already set `SSL_CERT_FILE`; verify `/etc/pki/tls/certs/ca-bundle.crt` exists |
| `ModuleNotFoundError: No module named 'geopandas'` | Conda env not activated | Run `conda activate nhm-gridmet` first |
| `Batch script contains DOS line breaks` | Windows line endings in shell scripts | `dos2unix <script>.sh` |
| `Job violates accounting/QOS policy` | Missing `--account` in sbatch | Add `--account=<your_account>` (find with `sacctmgr show association where user=$USER`) |

## Output

Each model produces these files in `domain_data/<model>/`:
- `nhru_GRIDMET_daily.nc` — Raw aggregated gridMET (K, mm)
- `nhru_weights_gridmet.csv` — Area-weight matrix (reusable, speeds up re-runs)
- `prcp.nc` — Precipitation (inches)
- `tmin.nc` — Min temperature (°F)
- `tmax.nc` — Max temperature (°F)

The last three are what pywatershed (notebook 4) expects as input.

## Performance Notes

- ~10 minutes per model on DTN (Internet2 speeds)
- ~100 minutes total for all 10 models (sequential)
- Bottleneck is OPeNDAP data transfer, not CPU
- gdptools handles internal parallelism for the aggregation step
- Weights are cached (`nhru_weights_gridmet.csv`) — re-runs skip this step
