# PEST++ IES posterior evaluation: pre/post streamflow KGE and recharge range

Status: plan, not started. Draft notebook exists at
`src/workflow_templates/pest/kge_pre_post_evaluation.py` (untested).

## Goal

1. Show, defensibly, whether calibration improved simulated streamflow.
2. Report a recharge estimate with a range, as committed to in the project scope.

## Decisions

- Post-calibration = the full iteration-3 posterior ensemble (500 realizations),
  not a single selected member. No selection step is needed for the headline
  results.
- Pre-calibration = a single run at `parval1` (the prior base parameters).
- All gages are evaluated together. Calibration gages were chosen as the best
  gages in each basin (minimal anthropogenic impact, record length), so they
  are not split out from other gages.
- Evaluation uses validation years only, and the split must match the one
  PEST used: odd = calibration, even = validation, in water years or calendar
  years per `ancillary/cal_year_config.csv` (see step 1).

## Steps

### 1. Confirm the cal/val split from the `.pst`

The GFv2 PEST templates split on the `water_years` workspace flag (default
`True` in `0_workspace_setup`). Notebook 00 writes it to
`ancillary/cal_year_config.csv`; notebook 01 and `forward_run_gfv2.py` read it
(missing file means calendar years). Odd years calibrate, even years validate.
Recharge is always calendar-year. The evaluation script reads the same file.

Still worth a one-time cross-check: parse the date token in streamflow
observation names in the final `.pst` and confirm the non-zero-weight years
match that flag. (`src/assist/pest/_gage_years.py` is a reporting script and
does not reflect the split.)

### 2. Run the posterior ensemble forward

- Source: `prior_mc_reweight.3.par.csv` (500 rows, includes `base`). Check that
  `base` survived all iterations.
- Run each realization through pywatershed on Hovenweep as a Slurm array job,
  one realization per task.
- Save per realization: daily `seg_outflow` at POI gages, and the recharge
  output used for the deliverable.
- Also run the prior (`parval1`) once with the same forcing, dates and gages.
- Optional check: whether `prior_mc_reweight.3.obs.csv` already holds the
  needed outputs, which would avoid the reruns for some metrics.

### 3. Streamflow: pre vs post on validation years

Per gage, on validation years only, monthly means of daily flow, months with
at least 20 days of observations:

- KGE (Gupta 2009) and components r, alpha, beta for the prior run.
- KGE for each of the 500 posterior members; summarize as median and 5–95%.
- Delta KGE = median posterior KGE minus prior KGE.
- Monthly climatology benchmark KGE (calibration-year monthly means), to show
  the model beats a seasonal-cycle baseline.
- Block bootstrap CI (resampling whole years) on delta KGE at key gages.

Across gages: one-sided Wilcoxon signed-rank test of delta KGE (post > pre),
plus the count of gages improved.

Note: use the median of per-member KGE, not KGE of the ensemble-mean
hydrograph. Averaging hydrographs smooths variability and biases alpha low.

### 4. Recharge range

- Report median recharge and the 5–95% band across all 500 members.
- Compare with the prior (iteration 0) spread. If the posterior is much
  narrower than is physically plausible, say so; IES ensembles can collapse,
  and prior-data conflict (dominated by `runoff_mon`) can pull members toward
  a compromise.
- Compare the band with the recharge target product's own range.

### 5. Sensitivity check (optional)

Repeat the recharge range for the subset of members whose low-flow KGE
(KGE on log flows) passes a threshold in calibration years. If the band is
similar to the full ensemble, the estimate is robust to that choice. This is
only needed as a check, or if a single deliverable parameter file is required;
in that case select on calibration years and report on validation years.

## Chaining onto the Hovenweep calibration run

Goal: one submission runs calibration, the posterior forward runs and the
evaluation, with no manual steps in between.

Slurm job dependencies (`--dependency=afterok:<jobid>`) chain three jobs:

1. **IES** — the existing `run_pestpp_ies.slurm` (or `_1node`).
2. **Posterior forward runs** — new `run_posterior_ensemble.slurm`, an array
   job (`--array=0-500%N`, 500 members plus one prior run). Each task reads its
   row from `<case>.<noptmax>.par.csv`, writes parameters, runs pywatershed,
   and saves gage `seg_outflow` and recharge to `posterior/real_<name>.nc`.
   Starts only if IES exits cleanly.
3. **Evaluation** — new `run_posterior_eval.slurm`, a single small job that
   runs `kge_pre_post_evaluation.py` as a script (no Jupyter) and writes CSVs
   and figures to `posterior/eval/`. Depends on the whole array finishing.

A `submit_calibration_chain.sh` generated by `06_hovenweep_pest_setup.py`
submits all three, using `sbatch --parsable` to capture each job ID.

Design notes:

- The final iteration number comes from the `.pst` (`noptmax`), not a
  hardcoded `3`. Abort job 2 with a clear message if that par file is missing
  or the `base` row was dropped.
- Use `afterok`, not `afterany`, so a failed IES run does not trigger 500
  wasted forward runs. Use `afterany` for job 3 so a few failed members still
  produce an evaluation; the script reports how many members are missing.
- The evaluation runs headless, so the draft notebook must work as a plain
  script (its `if __name__ == "__main__"` block) with paths set by arguments or
  environment variables, not edited cells.
- Environment on the cluster: reuse whatever the PEST workers already use to
  run pywatershed (the `remote-run` pixi environment, if that is what is
  shipped). The evaluation also needs scipy and xarray there.
- Alternative for job 2: rerun IES with `ies_par_en` set to the final par file
  and `noptmax = -1`, reusing the existing workers. Cheaper to set up, but it
  only yields outputs listed in the instruction files, so daily gage flow and
  recharge would need to be added there first. The array job is simpler.
- Throttle the array (`%N`) to fit the partition, same sizing logic as the
  IES worker count (about 9 GB per run).
